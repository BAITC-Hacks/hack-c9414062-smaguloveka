## 3. Основной пользовательский сценарий

### 3.1 Первый запуск

- Выбор папки записей и языка интерфейса; RU/KZ для основных рабочих экранов.
- Проверка разрешений записи, свободного места, доступности локальных движков и моделей.
- Установка моделей из заранее подготовленного каталога либо явная загрузка при наличии сети. Обработка после установки не требует внешних AI API.
- Тест микрофона и системного звука с индикатором уровня.
- Предлагаемый профиль M1 Pro / 16 ГБ: одна AI-задача одновременно, последовательная загрузка ASR, диаризации и LLM. Проверяется реальный пик памяти, включая KV-cache и временные буферы.
- Демо-встреча доступна сразу и явно обозначена как подготовленный пример. Она не засчитывается за живую проверку AI.
- Интеграции необязательны для записи, анализа и экспорта.

### 3.2 Новое совещание

- Ввести название, реальную дату/время и часовой пояс; при необходимости список участников, роли, повестку, словарь имён и терминов.
- Выбрать запись в помещении, запись онлайн-встречи через системный звук, импорт файла или подключённого бота.
- Для импорта дата загрузки не подставляется молча вместо даты совещания.
- Показать понятное уведомление о записи/ИИ. Автоматическое сообщение в чат возможно только через работающий адаптер; ручное уведомление фиксируется как ручное.
- Если разрешения отсутствуют, источник недоступен или модель не установлена, показать конкретное действие для исправления.

### 3.3 Запись и обработка

- Во время записи: таймер, индикатор источника, пауза/продолжение/завершение, сохранение аудио частями.
- Предварительная транскрипция допускает изменения; подтверждаемый результат формируется после итоговой обработки.
- Этапы: подготовка аудио → распознавание → разделение голосов → сопоставление реплик и участников → извлечение фактов/поручений → саммари → проверка человеком.
- Длинные встречи обрабатываются частями с последующей общей сверкой повторов, уточнений и сроков. Саммари не является единственным источником для извлечения поручений.
- После закрытия/сбоя приложение сохраняет завершённые этапы и предлагает продолжить незавершённую обработку. Отмена не удаляет исходную запись.
- Шум, пустая запись и тишина не должны порождать готовый выдуманный протокол.

### 3.4 Проверка

- Один экран объединяет плеер, реплики, саммари и поручения.
- Переход по цитате открывает реальный фрагмент аудио; время и текст берутся из базы, а не из свободного ответа LLM.
- Секретарь исправляет транскрипт, объединяет/разделяет ошибочные метки голосов, назначает людям имена.
- Для поручения доступны действие, ответственный, соисполнители при явном упоминании, срок, направление, источник и состояние проверки.
- Отсутствующий ответственный/срок отображается явно. Разрешено подтвердить поручение без срока с соответствующей отметкой; не всякая СЭД примет такой объект, и это проверяется до отправки.
- «Подтвердить все» не скрывает нерешённые замечания: пользователь видит их список и принимает решение.
- После правки исходного текста связанные извлечённые сведения помечаются как требующие повторной проверки.
- Повторное распознавание создаёт новую версию; ручные исправления и подтверждённый протокол не перезаписываются без сравнения.

### 3.5 Итог и доставка

- Подтвердить версию протокола и выбрать разделы PDF/DOCX.
- Нажать «Отправить», выбрать подключения и состав: документ, саммари, подтверждённые поручения, при необходимости транскрипт.
- Увидеть адресата и предварительный состав отправки. Для этого кейса аудио не включается в пакет доставки СЭД.
- Каждое подключение получает независимую операцию доставки; успешная доставка в одну СЭД не отменяется из-за ошибки другой.
- Получить внешние ID/ссылки там, где API их возвращает, либо честный статус «принято, требуется проверка результата».
- В локальном списке видеть сроки и статусы. Отправка в СЭД не означает выполнение поручения.

Роли «секретарь/руководитель/исполнитель» из макета не считаются авторизацией. Первая поставка — локальный профиль пользователя. Многопользовательский доступ требует серверной идентификации и контроля прав; это отдельное расширение, не скрытый переключатель роли.

## 5. Подключить свою СЭД

### 5.1 Модель подключений

Каждое подключение имеет собственные ID, название, тип адаптера, адрес, ссылки на секреты, выбранный контейнер/проект, правила сопоставления полей, сотрудников и статусов, разрешённый состав передачи, состояние и историю проверок.

Примеры независимых экземпляров: «СЭД головного офиса», «СЭД филиала», «Bitrix24 — поручения», «Внутренний API — архив». Два экземпляра одного типа не делят секреты, очередь или настройки.

Ни один адаптер не предполагает, что одноимённый сотрудник в двух системах — один и тот же человек. Сопоставление выполняется с внешним ID, при неоднозначности требуется выбор.

### 5.2 Мастер подключения

1. Название и тип: готовый коннектор, HTTP API/webhook или MCP.
2. Адрес внутри разрешённого контура и способ авторизации.
3. Проверка доступности/авторизации безопасным endpoint, когда он предусмотрен API.
4. Выбор операции: создать документ, создать поручение, добавить вложение, обновить поддерживаемый объект.
5. Выбор проекта/папки/типа документа и сопоставление обязательных полей.
6. Сопоставление сотрудников и статусов, правила дат/часовых поясов.
7. Предпросмотр запроса без раскрытия секретов.
8. Явно обозначенная тестовая отправка синтетического документа в тестовый контейнер и проверка результата.
9. Сохранение и включение подключения.

«Проверить соединение» не должен молча создавать настоящий документ. В Memora custom check выполняет POST с тестовым event: этот путь нужно адаптировать под фактический API, а не считать любой POST безвредным.

### 5.3 Адаптеры

| Тип | Включаемое поведение | Граница совместимости |
|---|---|---|
| HTTP JSON/webhook | Настройка тела, заголовков, сопоставлений, извлечение ID/URL из ответа | Для простых API или шлюза заказчика |
| HTTP multipart | Документ и метаданные, корректные MIME-типы/имена файлов | Сервер должен поддерживать такой контракт |
| Bitrix24 | Использование существующего клиента и метаданных портала; создание документа/задач по проверенному сценарию | Конкретные права и поля проверяются на портале |
| MCP | Чтение схем, выбор конкретного разрешённого инструмента, проверка аргументов | Наличие инструмента не гарантирует соответствие процессу СЭД |
| Специальный адаптер СЭД | Многошаговая загрузка, карточка документа, согласование, нестандартная авторизация | Нужны API-документация и тестовый доступ этой СЭД |

Универсальность — в расширяемом механизме и количестве подключений. Она не означает готовый коннектор к любому продукту без его API. Без API остаётся ручной импорт PDF/DOCX; это не отображается как действующая автоматическая интеграция.

### 5.4 Надёжность и безопасность доставки

- Секреты хранятся в системном хранилище, а не в SQLite, логах, репозитории или экспортируемом конфиге.
- В режиме кейса разрешены только заранее настроенные назначения внутри контура заказчика. Совместимость кода с облачным Teams/Bitrix не даёт разрешения отправлять туда данные.
- Перенаправления не должны пересылать авторизацию на другой адрес. Состав пакета фиксируется перед постановкой в очередь.
- Очередь переживает перезапуск приложения. Один отказ не блокирует остальные назначения.
- Ключ операции включает подключение, тип операции, внутренний ID объекта и версию. Повтор той же операции сохраняет ключ; правка документа — новая версия и осознанная операция обновления/создания.
- При 429 и временных сетевых ошибках — ограниченные повторы с задержкой и учётом Retry-After. При ошибке прав/полей — исправление настройки.
- При таймауте после отправки неизвестно, создал ли сервер объект. Если API поддерживает ключ идемпотентности/поиск по внешнему ключу, проверяем результат. Иначе автоматический повтор записи останавливается до сверки, чтобы не создать дубликат.
- Для последовательности «загрузить файл → создать карточку → создать задачи» сохраняются результаты каждого шага. Частичный успех отображается явно, повтор продолжает незавершённые шаги.
- 202 Accepted означает принятие операции, а не завершённую регистрацию; при наличии API выполняется проверка статуса.
- Десктопная очередь работает, пока приложение запущено. Для круглосуточной доставки потребуется отдельная служба/сервер.
- Обратная синхронизация статусов доступна только у адаптеров с нужным API. В первой версии — явное обновление из СЭД для поддержанного адаптера; при расхождении показываются локальный и внешний статусы с источником и временем. Универсальную двустороннюю синхронизацию не обещаем.

## 6. Онлайн-платформы: запись и боты

Три разных возможности не должны смешиваться:

1. Запись встречи, которую пользователь открыл в Zoom/Teams/Meet: локальный захват микрофона и системного звука. Включается в основную поставку.
2. Бот самостоятельно входит по ссылке и получает звук: отдельный платформенный адаптер. Входит в полную дорожную карту, но имеет внешние условия запуска.
3. Отправка итогов в канал Teams: исходящая доставка. Найденный модуль Memora Teams реализует именно её, а не бота-участника. В строгом контуре кейса облачная отправка отключена.

Для каждого бота нужны вход, приглашение/допуск организатором, уведомление о записи, получение аудио, завершение, обработка разрыва связи и проверка политик организации. При недоступности кнопка объясняет причину и предлагает локальную запись; успешное подключение не имитируется.

- Zoom: кандидат — официальный Meeting SDK и доступ к raw audio. Выбор платформы адаптера и необходимые разрешения проверяются отдельным экспериментом. [Документация](https://developers.zoom.us/docs/meeting-sdk/linux/).
- Teams: application-hosted media bots требуют Windows Server в Azure для production. Это не компонент, который можно просто упаковать в Mac DMG, и совместимость с закрытым контуром необходимо согласовать. [Требования Microsoft](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/calls-and-meetings/requirements-considerations-application-hosted-media-bots).
- Google Meet: рассмотренный Meet Media API находится в Developer Preview; текущий guide требует включения проекта, OAuth principal и участников в программу. Готовность определяется доступом к API и проверкой конкретной организации. [Документация Google](https://developers.google.com/workspace/meet/media-api/guides/get-started).

Если организаторы трактуют строку ТЗ о подключении участником как обязательность ботов всех трёх платформ, локальная запись не закрывает её полностью. Такой пункт в матрице приёмки остаётся открытым до реального прогона соответствующих ботов. Доступ к облачным платформам для самого совещания также нельзя путать с разрешением отправлять запись/текст в облачные AI API.

## 7. AI и модель данных

### 7.1 Распознавание и языки

- Сравнить локальный многоязычный Whisper с лицензированными адаптациями под RU/KK на одной независимой выборке.
- Сохранить исходные языки; перевод не подменяет транскрипцию.
- Измерить WER/CER отдельно для RU, KK и MIX; отдельно оценить имена, числа, даты и действия.
- Два файла кейса не доказывают казахский/MIX: добавить вручную проверенные записи разных говорящих.
- Дообучение запускается при подтверждённом дефиците качества готовых моделей. Пары «аудио — дословный текст», разделение train/test по людям и совещаниям, проверка русской и казахской речи на регрессии. Чувствительные данные остаются в разрешённом контуре.

### 7.2 Диаризация и имена

- Проверить CAM++/кластеризацию донора и альтернативный локальный pipeline на одинаковых записях.
- Проверять смену говорящего внутри одного фрагмента, короткие ответы, перебивания и похожие голоса.
- Отличать speaker ID от participant ID и от исполнителя поручения.
- Автоматическое предположение имени показывать как предположение до подтверждения; ручная привязка приоритетна.
- Голосовая биометрия не обязательна для выполнения базового ТЗ: отдельная опция после измерения ложных совпадений и разработки регистрации/удаления эталонов.

### 7.3 Поручения

Сущность поручения содержит:

| Поле | Смысл |
|---|---|
| id, meeting_id, protocol_version | Стабильная связь с совещанием и версией |
| title, description | Действие и существенные условия |
| assignee | Человек, подразделение или неизвестный; не обязательно говорящий |
| due_original | Формулировка из разговора |
| due_kind | Дата, интервал, относительный, событийный, отсутствует |
| due_date / interval / dependency | Нормализованный срок только при достаточном контексте |
| evidence | Ссылки на реальные сегменты и диапазоны времени |
| review_state, review_reasons | Черновик, требует проверки, подтверждено, отклонено |
| execution_state | В работе, выполнено, отменено; просрочка вычисляется по сроку |
| condition | Условие исполнения, если оно явно обсуждалось |
| external_links | Подключение, внешний ID, URL, состояние доставки |

Правила: не назначать поручение председателю только потому, что он его произнёс; не создавать дубли из финального резюме; учитывать явно согласованное изменение срока; не превращать предложение в утверждённое решение; не придумывать год или дату; конфликтующие формулировки сохранять с источниками для проверки.

Для второго примера отдельно учитывать смету за неделю и закрытие очереди обучения за месяц. Таблицы примеров — вспомогательный эталон, а не основание потерять обязательства из реплик.

## 9. Пакеты выполнения и приёмка

Большой объём делится на самостоятельные пакеты. Перед кодированием каждого составляется небольшой исполнимый план с конкретными тестами и изменениями; номер карточки берётся из восстановленной доски. Одна карточка — один scoped commit с её ID, затем review, решение done оставляется человеку.

### Пакет A — технический эксперимент и фиксирование основы

- [ ] Зафиксировать исходный commit Memora и перечень переносимых модулей, не менять донор.
- [ ] Запустить ASR/диаризацию/LLM на целевой машине с двумя файлами spec и независимыми RU/KK/MIX примерами.
- [ ] Записать версию движков, веса/квантование, настройки, длительность, пик RAM, ошибки имён/сроков и поручений.
- [ ] Выбрать модели по измерениям и определить необходимость дообучения.
- [ ] Отдельно проверить требования и доступы к каждому боту.

Приёмка: воспроизводимый отчёт с реальными результатами, без переноса заявленных метрик из чужих model cards как своих.

### Пакет B — приложение и интерфейс

- [ ] Создать изолированный профиль, собственный application ID, новую SQLite-схему и Tauri-команды.
- [ ] Перенести дизайн в React-компоненты и локальные стили/шрифты.
- [ ] Реализовать навигацию, пустые состояния, загрузку, ошибки, RU/KZ для основных сценариев и светлую/тёмную темы.
- [ ] Разделить демонстрационные и пользовательские данные.

Приёмка: приложение запускается без доступа к профилю Memora, ключевые экраны визуально сопоставлены с HTML, демоданные нельзя принять за результат реальной обработки.

### Пакет C — запись и локальный AI-конвейер

- [ ] Подключить запись/импорт, проверку источников и сохранение аудио.
- [ ] Создать очередь этапов с отменой и восстановлением после перезапуска.
- [ ] Подключить выбранные ASR/диаризацию, реальные таймкоды и редактирование участников.
- [ ] Проверить последовательную загрузку моделей и обработку длинной записи.

Приёмка: новая запись проходит реальную обработку без внешнего AI API; перезапуск не теряет сохранённое аудио; тишина, испорченный файл и отсутствие модели дают понятный результат.

### Пакет D — протокол и поручения

- [ ] Определить schema поручений/сроков/evidence и миграции.
- [ ] Сначала закрепить тестами: отсутствующий срок, исполнитель-подразделение, невыступающий исполнитель, изменение срока, повтор, условное решение, два обязательства с разными сроками.
- [ ] Реализовать извлечение с проверкой источников и сверкой по всему совещанию.
- [ ] Добавить редактирование, подтверждение, версии, локальные статусы и ссылки на аудио.
- [ ] Подключить реальный PDF/DOCX с проверкой кириллицы и казахских букв, таблиц и переноса страниц.

Приёмка: все перечисленные случаи проходят на фиксированных транскриптах; на аудио дополнительно оцениваются ошибки ASR. Число поручений не подгоняется под число строк исходных таблиц.

### Пакет E — несколько СЭД

- [ ] Перенести модель независимых именованных подключений и безопасное хранение секретов.
- [ ] Реализовать мастер HTTP JSON/multipart, field mapping, assignee mapping и обработку ответа.
- [ ] Адаптировать выбранный готовый коннектор Bitrix24 и MCP-клиент под новый контракт поручений.
- [ ] Реализовать persistent outbox, идемпотентность с учётом возможностей адресата, частичный успех и восстановление многошаговой доставки.
- [ ] Подготовить локальный стенд СЭД с синтетическими данными, ошибками 401/429/500, задержками и повторными запросами.
- [ ] Проверить хотя бы одну реальную СЭД в тестовом контуре заказчика. До этого статус — «проверен контракт на стенде», а не «проверено у заказчика».

Приёмка: три подключения одновременно получают выбранную версию; отказ одного не затрагивает два других; секреты отсутствуют в логах; при неопределённом результате нет слепого повторного создания.

### Пакет F — платформенные боты

- [ ] Для каждого из Zoom/Teams/Meet подтвердить доступный официальный способ входа и получения аудио.
- [ ] Реализовать адаптер, регистрацию, разрешения и сценарии допуска/отказа/разрыва.
- [ ] Подключить звук адаптера к общему локальному конвейеру.
- [ ] Проверить реальную тестовую конференцию и фактическое место обработки/передачи данных.

Приёмка для КАЖДОЙ платформы: реальный вход участником, уведомление, получение аудио, корректное завершение, протокол из полученного звука. Невыполненные внешние условия фиксируются как блокер этого адаптера; захват системного звука не меняет его статус на готово.

### Пакет G — поставка и демонстрация

- [ ] Собрать DMG и автономный пакет моделей с версиями, размерами, контрольными суммами и лицензиями.
- [ ] Проверить установку на чистом пользовательском профиле, наличие sidecar и разрешения записи.
- [ ] Определить и проверить способ подписи/нотарификации для беспрепятственной установки у заказчика; не считать ad-hoc подпись равнозначной Developer ID.
- [ ] После подготовки моделей отключить интернет и повторить обработку/экспорт. Интеграции проверяются отдельно в разрешённой локальной сети.
- [ ] Подготовить README, инструкции подключения СЭД, архитектурную схему, пример результата, ограничения и отчёт тестов.
- [ ] Пройти независимое ревью изменений и полный пользовательский прогон.

Приёмка: другой человек устанавливает приложение по инструкции, обрабатывает новую запись и получает документ; инженерные инструменты сборки не нужны конечному пользователю.

| Требование | Реализация | Доказательство |
|---|---|---|
| Русская речь | Локальный ASR | Размеченный RU-набор и реальные записи |
| Казахская речь | Выбранный ASR | Отдельный KK-набор |
| Смешанная речь | Выбранный/адаптированный ASR | MIX внутри реплики и между репликами |
| Диаризация | Локальный движок + подтверждение имён | Сравнение со спикерной разметкой |
| Поручение/ответственный/срок | Структурированное извлечение и проверка | Эталонные случаи и прослушивание источников |
| Саммари | Локальная LLM с evidence | Отсутствие неподтверждённых фактов при проверке |
| PDF/DOCX | Локальный экспорт | Открытие файлов и визуальная проверка |
| Закрытый контур | Локальные модели и разрешённые СЭД | Автономный прогон и проверка сетевого поведения |
| Запись/импорт | Аудиомодуль | Реальная новая запись и импорт |
| Участник Teams/Zoom/Meet | Отдельные адаптеры | Реальная конференция для каждой платформы |
| Интеграция с СЭД | Мастер + адаптеры + очередь | Стенд и доступная тестовая СЭД |
| Дашборд поручений | Статусы, сроки, фильтры | Изменение задачи отражается в представлениях |

| Календарь | Следующий этап по решению пользователя | Не входит в первую поставку |

Основной сценарий записи/транскрипции/поручений/саммари/экспорта покрывается планом полностью. Сценарий автоматических напоминаний сознательно отложен. Полное покрытие формулировки о ботах всех платформ нельзя заявлять до их фактической проверки.

## 11. Что требуется от заказчика для конкретной СЭД

Документация API или схема MCP-инструментов; тестовый адрес; способ выдачи доступа; тип документа/задачи; обязательные поля; справочник сотрудников и их внешние ID; разрешённые назначения; тестовый контейнер; пример ожидаемого результата. Секреты вводятся в приложение, а не в план, карточки или чат.

До получения этих материалов разработка ядра, UI, HTTP-коннектора и локального интеграционного стенда не блокируется. Отсутствие доступа блокирует только доказательство совместимости с конкретной системой.

## 12. Финальная демонстрация

1. Открыть приложение с подготовленными локальными моделями.
2. Загрузить новую запись или записать короткое совещание с RU/KK/MIX.
3. Дождаться фактического завершения обработки, показать время и параметры машины.
4. Проверить голоса, перейти от поручения к аудиофрагменту.
5. Исправить имя/срок и подтвердить протокол.
6. Сохранить PDF/DOCX и открыть документы.
7. Выбрать две разрешённые интеграции, показать реальные созданные объекты.
8. На стенде показать отказ третьей интеграции, журнал и безопасное восстановление.
9. Отдельно продемонстрировать ботов тех платформ, для которых выполнены условия доступа и готова реализация.

Ни тестовые результаты, ни отправки-заглушки, ни переключатели ролей не выдаются за промышленную работу. Дизайн сохраняется, а заявленные возможности соответствуют проверенному поведению.
